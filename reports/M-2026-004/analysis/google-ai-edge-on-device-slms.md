## 2. 핵심 주장 — 저자/발표 주장의 층위

1. **지원 모델군을 초기 4개에서 12개 이상으로 넓혔다.** Google AI Edge는 전년도 Android·iOS·Web용 초기 4개 온디바이스 SLM 지원에서 Gemma 3·Gemma 3n을 포함한 12개 초과 모델 지원으로 확장했다고 발표한다. 모델은 LiteRT Hugging Face Community에 호스팅된다고 한다.  
   *위치: 원문 375행, 첫 문단.*

2. **Gemma 3n을 멀티모달 온디바이스 SLM의 early preview로 제공한다.** 저자는 Gemma 3n을 Gemma의 첫 멀티모달 온디바이스 SLM으로 소개하며 텍스트·이미지·비디오·오디오 입력을 지원한다고 주장한다. 같은 문단은 RAG 및 Function Calling 라이브러리와의 결합으로 완전한 엣지 환경에서 기능을 시제품화·구축할 수 있다고 제시한다.  
   *위치: 원문 375행, 둘째 문단.*

3. **int4 사후학습 양자화가 모델 크기·지연·피크 메모리를 줄일 수 있다.** 최신 양자화 도구가 더 높은 품질의 int4 post-training quantization을 제공하며, 많은 모델의 기본 데이터형으로 서술된 bf16과 비교해 언어 모델 크기를 2.5–4배 줄이고 지연 및 피크 메모리 소비를 유의미하게 낮출 수 있다고 발표한다.  
   *위치: 원문 392행, ‘Broader model support’의 세 번째 문단.*

4. **Gemma 3 1B의 작은 배포 크기와 모바일 GPU pre-fill 처리량을 제시한다.** 저자는 Gemma 3 1B가 529MB이며 모바일 GPU에서 초당 최대 2,585토큰 pre-fill을 실행할 수 있어, 최대 한 페이지 분량을 1초 미만에 처리할 수 있다고 말한다.  
   *위치: 원문 392행, ‘Gemma 3 1B & Gemma 3n’의 첫 문단.*

5. **온디바이스 RAG는 미세조정 없이 앱 특화 데이터를 SLM에 연결하는 수단이다.** 저자는 RAG가 애플리케이션 특화 데이터로 SLM을 보강하고, 1,000페이지 정보 또는 1,000장의 사진에서 관련성이 높은 일부 조각을 찾아 모델에 제공할 수 있다고 설명한다. AI Edge RAG 라이브러리는 지원 SLM과 작동하고 Android에서 현재 이용 가능하며, 데이터베이스·청킹·검색 함수를 바꿀 수 있다고 한다.  
   *위치: 원문 409행, ‘Bringing context…RAG’의 두 문단.*

6. **온디바이스 Function Calling은 앱 함수 등록·응답 파싱·함수 호출을 제공한다.** Android에서 현재 이용 가능한 AI Edge Function Calling 라이브러리가 온디바이스 언어 모델 통합, 애플리케이션 함수 등록, 응답 파싱, 함수 호출에 필요한 유틸리티를 포함한다고 발표한다. 사전 정의된 애플리케이션 함수 또는 API를 언제 호출할지 모델이 결정하게 한다는 설명도 포함한다.  
   *위치: 원문 409행, ‘Enabling action…function calling’의 첫째·둘째 문단.*

## 3. 원문이 제시한 근거·관찰 — 주장과 분리

원문은 위 기능들을 뒷받침하는 **정량 벤치마크 표, 실험 설계, 원시 측정값**을 제시하지 않는다. 제시된 것은 배포/기능 범위의 설명, 특정 수치, 사용 예시 및 데모 설명이다.

- **배포 및 지원 범위의 서술:** LiteRT Hugging Face Community에서 모델을 선택·다운로드해 온디바이스에서 실행할 수 있고, 해당 모델들은 모바일·웹용으로 변환·최적화되었다고 원문은 서술한다. 사용자 맞춤화 절차로는 베이스 모델 미세조정 후 AI Edge 라이브러리로 변환·양자화하는 흐름을 제시하며, Gemma 3 1B 미세조정·변환 Colab을 언급한다. 이는 기능/워크플로의 발표 근거이지, 성능을 재현·비교한 결과는 아니다.  
  *위치: 원문 392행, ‘Broader model support’의 첫째·둘째 문단.*

- **모델 변형 및 가용성:** Gemma 3n의 변형은 **E2B·E4B 유효(effective) 파라미터 표기**로 구분해야 한다. `E` 표기는 총 파라미터 수가 아니라 유효 파라미터를 뜻하며, 교차검증에 인용된 공식 기술 정의상 E2B도 표준 실행에서 5B를 초과하는 총 파라미터를 로드한다. 따라서 이를 단순한 2B·4B 총 파라미터 변형으로 읽으면 안 된다. 원문 발표는 텍스트·이미지·비디오·오디오 입력을 지원하는 멀티모달 모델로 소개하되, 당시 Hugging Face에서 제공되는 것은 텍스트·이미지 모달리티이며 오디오는 곧 뒤따를 예정이라고 명시한다. 따라서 ‘4개 모달리티 지원’이라는 상위 발표와 ‘발표 시점의 실제 제공 모달리티’는 구분해야 한다.  
  *위치: 원문 392행, ‘Gemma 3 1B & Gemma 3n’의 둘째 문단(모달리티·가용성); E2B/E4B 정의 및 표준 실행 시 총 파라미터 범위: `verify/verification.md` V06의 교차검증 인용 공식 Gemma 3n model overview.*

- **기능 시연/사용 시나리오:** 비디오 설명은 온디바이스 SLM과 function calling 라이브러리로 사용자가 앱을 제어할 수 있다는 시연을, 다른 비디오는 Gemma 3n의 완전 온디바이스 이미지 분석을 설명한다. 본문은 연결이 없는 현장 기술자의 부품 사진 질의, 양손이 바쁜 창고·주방 근로자의 음성 재고 갱신을 예시로 든다. 이들은 적용 가능성의 사례이지 실제 현장 도입·성능 측정의 보고는 아니다.  
  *위치: 원문 378–389행(첫 비디오·설명), 395–405행(둘째 비디오·설명), 409행 RAG 직전 문단.*

- **RAG 파이프라인의 구성 가능성:** 지원 SLM과의 호환, 사용자 정의 데이터베이스·청킹 방법·검색 함수 변경 가능성, Android 현재 제공 및 추가 플랫폼 예정이 서술된다. 이는 라이브러리 인터페이스/가용 범위의 진술이며, 검색 품질·응답 품질·저장공간·지연의 측정치는 제공되지 않는다.  
  *위치: 원문 409행, RAG의 둘째 문단.*

- **Function Calling의 보조 수단:** Python tool simulation library는 특정 함수용 커스텀 언어 모델을 만들기 위한 합성 데이터 생성 및 평가를 돕고, 온디바이스 function calling 정확도를 높인다고 저자는 말한다. 그러나 데이터 생성 방식, 평가 지표, 기준선 및 향상 폭은 본문에 없다.  
  *위치: 원문 409행, Function Calling의 셋째 문단.*

### 원문이 정의하거나 설명한 개념

- **SLM:** ‘small language models’의 약어로 사용된다. 본문은 온디바이스에서 실행되는 SLM 지원을 다루지만, 파라미터 규모 또는 SLM 분류 기준을 일반적으로 정의하지는 않는다.  
  *위치: 원문 375행, 첫 문단.*
- **RAG (Retrieval Augmented Generation):** 미세조정 없이 애플리케이션 특화 데이터로 SLM을 보강하고, 큰 자료 집합에서 관련 조각을 찾아 모델에 넣는 방식으로 설명된다.  
  *위치: 원문 409행, RAG 첫 문단.*
- **int4 post-training quantization:** 원문은 bf16과 대비해 언어 모델 크기, 지연, 피크 메모리를 낮출 수 있는 양자화 체계로만 설명한다. bit 폭 이외의 알고리즘·캘리브레이션·정확도 평가 방법은 정의하지 않는다.  
  *위치: 원문 392행, ‘Broader model support’ 셋째 문단.*
- **Function Calling:** 모델이 애플리케이션 안의 사전 정의 함수/API 호출 시점을 결정하고, 라이브러리가 함수 등록·응답 파싱·호출을 지원하는 기능으로 설명된다.  
  *위치: 원문 409행, Function Calling 첫째·둘째 문단.*

### 방법론/측정 범위 판독

원문에 독립된 실험 방법론은 없다. 수치가 붙은 성능 진술은 Gemma 3 1B의 모바일 GPU pre-fill 속도와 int4 대 bf16 크기 감소뿐이며, 기기 모델, GPU 구성, 런타임/버전, 배치 크기, 입력·출력 토큰 길이, 정밀도(속도 수치의 경우), 반복 횟수, 지연 정의, 메모리 측정법 및 정확도 지표가 적혀 있지 않다. 따라서 이 수치들은 원문이 발표한 조건 제한적 수치로만 읽어야 한다.

## 5. 원문 한계 및 확인 필요 항목

1. **출처 편향과 근거 형식:** 공급자 발표문이며, 외부 검증이나 재현 실험을 제공하지 않는다. ‘fully optimized’, ‘much higher quality’, ‘significantly decreasing’, ‘increasing the accuracy’는 평가 방법과 결과표 없이 제시된다.  
   *위치: 원문 392행(모바일·웹 최적화, int4 품질/자원 주장), 409행(Function Calling 정확도 주장).*

2. **성능 수치의 재현 조건 부재:** 2,585 tokens/s와 2.5–4배는 하드웨어·런타임·모델 설정·측정 프로토콜이 빠져 있어 다른 기기나 워크로드로 일반화할 수 없다. 특히 토큰/초 수치는 **pre-fill**로 한정되어 있으며 생성 단계의 처리량이나 end-to-end 지연을 뜻한다고 볼 수 없다.  
   *위치: 원문 392행, 관련 두 문단.*

3. **멀티모달 기능의 발표 범위와 당장 가용한 범위의 차이:** Gemma 3n은 네 입력 모달리티를 지원한다고 소개되지만, 원문은 텍스트·이미지만 Hugging Face에서 이용 가능하고 오디오는 뒤따를 예정이라고 명시한다. 비디오의 실제 공개 상태와 각 모달리티별 성능은 이 문서만으로 확정할 수 없다.  
   *위치: 원문 392행, Gemma 3n 둘째 문단.*

4. **플랫폼 범위의 제한:** RAG·Function Calling 라이브러리는 원문상 Android에서 ‘today’ 이용 가능하고 다른 플랫폼은 후속 예정이다. 초기 문단의 Android·iOS·Web SLM 지원 확대와, 이 두 라이브러리의 플랫폼 가용성을 동일시하면 안 된다.  
   *위치: 원문 375행 첫 문단; 409행 RAG 둘째 문단 및 Function Calling 첫째 문단.*

5. **RAG 및 Function Calling 품질·비용 미확인:** 원문은 RAG의 검색 품질·인덱싱/저장공간·지연·오프라인 동작 조건, Function Calling의 함수 선택/인자 추출 정확도·오류 처리·안전 통제·합성 데이터 평가 설계를 보고하지 않는다. 이 항목들은 본문이 확립하지 않은 사항으로, 연결 문서나 별도 실험으로 확인이 필요하다.  
   *근거 위치: 원문 409행의 기능 설명에는 해당 측정·절차가 제시되지 않음.*

6. **향후 계획은 현재 기능의 증거가 아니다:** 저자는 최신 SLM 및 새 모달리티 지원, RAG·Function Calling의 기능·플랫폼 확장을 계속하겠다고 예고한다. 이는 로드맵 진술이므로 현재 제공 범위나 달성된 성능으로 읽을 수 없다.  
   *위치: 원문 409행, ‘What’s next’의 첫 문단.*

7. **E2B/E4B 명칭의 정의 확인 필요:** 이 발표 원문은 E 표기의 정의나 총 파라미터 수를 설명하지 않는다. 교차검증에서 인용된 공식 Gemma 3n model overview는 E2B·E4B를 유효 파라미터로 정의하고 E2B의 표준 실행이 5B를 초과하는 총 파라미터를 로드한다고 설명한다. 그러므로 본 원문의 ‘2B·4B’ 식 표현만으로 총 파라미터 규모를 확정해서는 안 된다.
