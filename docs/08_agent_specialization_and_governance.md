## 1. 문제의식 (Sam의 통찰 — 옳다)

> "잡다한 모든 일에 투입되는 에이전트는 역할 정체성에 오염이 생겨서, 많은 일에 투입될수록
> 전문화되는 것이 아니라 전문성이 떨어진다."

이 판단은 **옳다.** 하나의 에이전트에 서로 무관한 역할을 계속 얹으면:
- **SOUL(정체성) 오염**: 행동 원칙이 뭉개져 판단이 평범해진다(제너럴리스트化).
- **메모리 오염**: 서로 무관한 경험이 섞여 신호 대 잡음이 낮아진다.
- **도구·권한 비대화**: 모든 도구를 갖게 되어 보안 격리가 무너진다(권한 스코프는 profile 단위).
- **컨텍스트 낭비**: 매 작업마다 무관한 지식이 로드되어 비용↑·품질↓.

결과적으로 "많이 시킬수록 나빠지는" 반(反)복리가 된다. 회사의 목표(시간이 지날수록 좋아짐)와 정면 충돌한다.

**따라서 전문화는 선택이 아니라 성장의 전제조건이다.** 이것이 Option B(전문 profile) 채택의 핵심 근거이기도 하다([ADR-004](./06_design_decision_log.md)).

## 2. 4계층 전문화 스택

각 전문 profile은 **좁은 역할** 하나에 다음 4계층을 정렬한다. (그림: [`07`](./07_diagrams.md) §9)

| 계층 | 내용 | 범위 | 성장 방식 |
|------|------|------|-----------|
| **① SOUL.md (정체성)** | 이 에이전트가 누구이고 무엇만 하는가 + 행동 원칙 | **단일 역할로 한정** | 역할 경계 유지·정제(오염 방지) |
| **② Skill (절차)** | 그 역할의 반복 가능한 표준 방법론 | 역할 관련 skill만 | Reflection으로 개정(버전↑) |
| **③ Memory (역할 누적 경험)** | 그 역할 수행에서 얻은 교훈·선호·패턴 | 역할 범위 내 사실만 | 미션마다 축적, 정기 위생관리 |
| **④ Knowledge (공유 지식)** | LLM Wiki의 도메인 지식(공용) | 전 사(全社) 공유 | Curator가 수요 기반 축적 |

- ①②③은 **profile 전용**(각자 격리) → 전문성이 개인에게 누적.
- ④는 **공유**(LLM Wiki) → 지식은 회사 자산으로 공용. 전문성(개인)과 지식(공용)을 분리하는 것이 핵심.

> 예: `Reader` profile은 "논문 심층분석"만 한다. SOUL=분석가 정체성, Skill=PRISMA 분석·근거추출, Memory="이 저널은 방법론 섹션이 약함" 같은 누적 감각, Knowledge=Wiki의 해당 분야 개념. 미션을 거칠수록 Reader는 **더 나은 분석가**가 된다.

## 3. 거버넌스 규칙

### 3.1 구성 원칙
1. **1 profile = 1 역할.** 무관한 역할을 한 profile에 얹지 않는다.
2. **과적재 금지.** 역할이 커지면 profile을 **분리**(split)한다(예: Reader가 논문·코드 둘 다 무거워지면 Code-Reader 분리).
3. **작성자 ≠ 검증자.** 산출물 생산 역할과 검증 역할은 서로 다른 profile(코드 구현≠검증 포함, [ADR-006](./06_design_decision_log.md)).
4. **도구 최소권한.** 각 profile은 역할에 필요한 도구/MCP만(권한 스코프=profile 단위). 예: 코드 실행 권한은 Implementer만.

### 3.2 수명주기 (Lifecycle)
```
후보 역할 식별 → profile 생성(좁은 SOUL) → 제한 미션 투입 →
성과·전문성 평가 → (오염/과부하 시)분리 or (저활용 시)통폐합 → 승격/보존
```
- **생성**: 반복 수요가 증명된 역할만 profile로. (개념 문서 §11 인큐베이터와 연결)
- **분리**: 역할이 이질적으로 커지면 split.
- **폐기/통폐합**: 거의 안 쓰이면 archive(profile distribution으로 보존 가능).

### 3.3 SOUL.md 리뷰 & 메모리 위생
- **SOUL 리뷰**: 정기적으로 각 SOUL.md가 여전히 단일 역할인지 점검(정체성 드리프트 탐지).
- **메모리 위생**: 역할과 무관한 항목 유입 시 제거. 오래된 사실 갱신. (Memory는 작게 유지 — Hermes 원칙)
- **Skill 리뷰**: 중복·낡은 skill 정리, Reflection 기반 개정.

## 4. Solomon 예외 (제너럴리스트지만 역할은 한정)

Solomon(AI CEO)은 여러 도메인을 다루는 **제너럴리스트**지만, 그 역할은 **"기획·오케스트레이션·검증총괄·보고"로 엄격히 한정**된다.
- Solomon은 **실무(조사·집필·코딩)를 하지 않는다** → 실무 역량 오염이 없다.
- Solomon의 전문성은 "미션 설계·게이트 검증·조율"이라는 **단일 메타 역할**에 누적된다.
- 즉 Solomon도 "1 역할" 원칙을 지킨다(그 역할이 관리일 뿐).

## 5. 전문화 측정 (성장 지표와 연결)

전문화가 실제로 작동하는지 숫자로 본다([`02`](./02_company_design.md) §6 성장지표와 연동):
- 역할별 **재작업률↓**(검증 반려 감소)
- 역할별 **소요시간↓**
- 역할 **Skill 수·성숙도↑**, **Memory 유효 항목↑**
- **오염 신호**: 한 profile의 무관 역할 코멘트 비율, SOUL 드리프트 횟수 → 임계 초과 시 split.
